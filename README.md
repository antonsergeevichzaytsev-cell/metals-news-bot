# metals-news-bot

Название историческое: репо начиналось как новостной дайджест, сейчас это
связка из **десяти автоматизаций** на GitHub Actions с общим состоянием в JSON,
тестами и eval-харнессом. Pure Python stdlib, без pip-зависимостей.
Хостинг — публичный репо, стоимость Actions $0.

Выход у всех один — Telegram @antonmining_bot.

---

## Карта: кто когда просыпается

Время MSK, все расписания — будни, кроме недельного сторожа.

| Время | Что | Файл | Зачем |
|---|---|---|---|
| 07:45 | Mission Control | `mission_control.py` | утренний брифинг: urgent, pipeline, что делать сегодня |
| 08:00 | Anton Daily | `daily_brief.py` | фраза дня из `phrases.json` + пятничный F-блок |
| 08:00 / 20:00 | Metals & Mining digest | `digest.py` | рыночный фон из Google News |
| 08:30 … 01:00 (5×) | Filings watcher | `filings.py` | первичные релизы junior/mid miners |
| 09:00 | LinkedIn ideas | `linkedin_ideas.py` | тема поста из размеченных хуков или digest |
| 10:00 … 18:00 (5×) | Inbox consolidator | `inbox.py` | почта 8 экспертных платформ через IMAP |
| 10:00–18:30 (каждые 30 мин) | Pipeline sync | `pipeline_sync.py` | лиды из SENT, живые ответы, черновики follow-up |
| 13:15 / 17:15 | Account watch | `account_watch.py` | новости по компаниям, которые уже в работе |
| 18:30 | Evening digest | `evening_digest.py` | что изменилось за день, взгляд назад |
| Вс 19:00 | Weekly Check | `weekly_check.py` | сторож: живы ли сами боты + метрики недели |
| по событию | Alert on failure | — | падение любого workflow → Telegram |
| на push | Static check | — | тесты и статические проверки |

Разделение труда там, где оно неочевидно:
- **Mission Control vs Anton Daily** — деньги и действия против вооружения на день. Ноль пересечения.
- **Mission Control vs Evening digest** — те же данные, разный срез: утром «что делать», вечером «что произошло».
- **Pipeline sync vs Account watch** — про одну компанию, но разные каналы сигнала: первый читает почту, второй новости.
- **filings vs digest** — повод написать против фона для чтения.

## Общие модули

- `net.py` — retry/backoff для HTTP и IMAP. До 28.07.2026 любой транзиентный
  сбой Gmail/Telegram/DeepSeek валил прогон целиком, следующая попытка только
  по расписанию (до 24ч простоя). Ретраятся 429/5xx и обрывы, 4xx — нет.
- `cadence.py` — единый источник правды по каденции follow-up.
  Раньше константы жили тремя независимыми копиями в `pipeline_sync`,
  `mission_control` и `weekly_check`; они были синхронны, но вручную.
  Правило переноса: сюда идёт только логика, ИДЕНТИЧНАЯ во всех потребителях.

## Тесты и eval — разные вещи

`tests/` (12 файлов) проверяет детерминированную логику: regex-префильтр,
разбор вердиктов, каденцию, сеть. Запуск — `static_check.yml` на каждый push.

`eval_filings.py` проверяет то, что тестами проверить нельзя: принимает ли
DeepSeek-гейт **хорошие** решения. LLM недетерминирован, «правильный» ответ —
вопрос человеческого суждения, а не assert. Единственный источник правды —
разметка Антона. Порог `MIN_LABELS_FOR_VERDICT = 20`: ниже него проценты
вводят в заблуждение, и скрипт честно отказывается их считать, а не рисует
метрики на пустоте.

## Принцип: слепота хуже поломки

Тихий отказ выглядит как отсутствие событий, поэтому:

- `fetch` возвращает **причину** отказа, не `None`; статус `0 items` ловит
  смену формата при HTTP 200;
- алерт по ленте — по фронту статуса и только после подтверждения на двух
  прогонах подряд, чтобы однопрогонный timeout не ныл пять раз в день;
- отказы модели пишутся с причиной и флагом `orbit` — иначе не узнать,
  режет она мусор или целевую географию;
- срабатывания regex-префильтра сэмплируются — это слепая зона до модели;
- цифры прогона в `state[...]["last_run"]`: лог Actions без токена не
  читается, а state читается через `raw.githubusercontent`;
- боты, которым нечего сказать, **молчат**, но пишут `last_run` — сторож
  в `weekly_check` отличает «тихо» от «умер».

## Два бота подробно

### digest.py — рыночный фон
32 RSS-запроса → отсечка 48ч → чёрный список источников → ключевики
(`keywords.txt`) → дедуп по хэшу ссылки → near-dup по пересечению токенов
заголовка (Jaccard ≥ 0.5, сигнатуры переживают прогон) → **сортировка
орбита-первой** → DeepSeek → Telegram двумя блоками: 🎯 Цели (только `high`)
и 🧠 Контекст.

Кап `MAX_ITEMS_PER_RUN = 12` упирается каждый прогон, поэтому порядок
сортировки определяет, на что тратится бюджет модели.

### filings.py — повод написать
11 лент → дедуп → отсечка 36ч → **бесплатный regex-префильтр** (режет ~26%:
размещения, назначения, AGM, конференции, разведочные пробы) → сортировка
орбита-первой → DeepSeek со стадийным гейтом → Telegram, одно сообщение
на элемент.

Стадийный гейт — главное в промпте: каждый навык продаётся только на своей
стадии. Началась стройка — FEL и оценка затрат позади, предлагать их нельзя.
В промпте лежит контрастный пример: неправильный ответ рядом с правильным.
`low` в Telegram не уходит, только в историю — есть на чём калибровать порог.

Тихие часы 23:00–08:00 MSK: ночной улов копится в `pending`, уходит утром.

## Почему боты себя не правят

Решение от 17.07.26, не пересматривать без цифр. Выборка меток мала —
правка промпта на ней будет подгонкой под шум. Суждение остаётся за человеком.
Самоправящийся фильтр может тихо съехать в «резать всё» при зелёном прогоне.

## Setup

Secrets: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `DEEPSEEK_API_KEY`,
плюс доступы Gmail для `inbox.py` и `pipeline_sync.py`.

Все пишущие workflow сидят в одной concurrency-группе `repo-writes`
с `queue: max` — без этого GitHub отменяет все pending-прогоны в группе
кроме последнего (найдено 21.07: так потерялись 4 из 8 ручных dispatch).
Пуш состояния — с rebase и повторами.
